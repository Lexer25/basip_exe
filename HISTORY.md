basip_ctrl_panel - History

Версия: 2.0.4.0
1. Адрес журнала событий выбирается по мажорной версии API панели: для 1.x — GET /api/v1/log/list
   с фильтром filter=timestamp+ge+<метка времени в мс>, для 2.x и выше — GET /api/v1/log/items
   с параметром from. Раньше всегда запрашивался log/items, и панели 1.x (прошивка 3.13.x)
   отдавали системный журнал (вход в веб-интерфейс) вместо журнала проходов.
2. Каждая строка журнала помечается панелью сразу после уровня: "[DBG][617] текст" — запись об
   обработке панели, "[DBG][sys] текст" — запись не связана с панелью (запуск, итерация, таймаут,
   ошибки запуска, служебные сообщения хоста). Тексты сообщений при этом не изменялись.
3. Параметр Log:LogLevel теперь задаёт уровень журнала для категорий приложения (Basip.*):
   Worker, DB, Device, Basip.DebugOutput, StartupFailureService. Раньше он применялся только
   к файловому приёмнику, а общий фильтр отсекал Debug и Trace, поэтому отладочные записи
   (в том числе дампы запросов и ответов) в файл не попадали.
4. При каждом запуске в журнал пишется версия программы и путь к исполняемому файлу; в строку
   "126 timeout basip" добавлено время следующего запуска; результат запроса журнала пишется
   строкой "455 GetLog result: status=..., body=...".
5. Незаполненная конфигурация больше не приводит к падению с необработанным исключением: причина
   пишется в журнал (в том числе в файл), служба завершается с кодом возврата 1. Если каталог
   журнала недоступен на запись, журнал ведётся в первом доступном каталоге.
6. Версии приведены к 2.0.4.0: приложение (Basip.csproj), установщик (BasipSetup.iss), build.bat.
   README обновлён под текущее поведение (формат строки журнала, уровни, адрес журнала, отладка
   на одной панели).
7. За одну итерацию забираются ВСЕ страницы журнала, накопившиеся с метки LASTEVENT, а не только
   одна: раньше за прогон обрабатывалось не более limit (50) событий, поэтому накопление в 1000
   событий требовало 20 запусков. Страховка — не более 200 страниц (10 000 событий) за итерацию,
   остаток забирается следующей (пишется предупреждение).
8. Номер идентификатора (карты) в событии разбирается для обоих вариантов API: у 1.x он лежит
   прямо в info (info.number), у 2.x — в info.model (info.model.number). Раньше читался только
   info.model, поэтому на панелях с API 1.x карта в событии не определялась и в событие СКУД
   уходил пустой note. Разбор вынесен в LogItem.IdentifierNumber: ключи number, card, code, owner,
   значение принимается и строкой, и числом. В LogInfo добавлен приём неизвестных полей
   ([JsonExtensionData]), поэтому поля API 1.x (type, apartment_address, localized и т. д.)
   доступны как info.fields.

   JsonDocument.Parse больше не падает на не-JSON теле.

   на параметры вместо подстановки значений в текст запроса.

11. Environment.Exit(1) заменён на штатную остановку хоста через IHostApplicationLifetime.
12. Удалён неиспользуемый код: DeviceInfo.cs, _EventInsert, GetAllEventTypes, EventType,
    InitializeEventTypeMapping, ConvertNameToKey, неиспользуемые using и поле hashPassword.
13. Версии приведены к единому значению 2.0.3.4: приложение, установщик, README.
14. Исправлен ярлык "Просмотр логов" в установщике: указывал на {app}\logs\app.log
    вместо фактического C:\ProgramData\Basip\ArtonitBasIpTools.log.
15. Сборка проходит без ошибок и предупреждений.

Дата: 13.10.2026

2. Device.GetEvents реализован как getEvent() из basoop.php: сначала пробный запрос

   страницы журнала ceil(total_items / limit) — там самые свежие события.

4. Если все события умещаются в одну страницу, повторный запрос к панели не выполняется
   (в basoop.php в этом случае всегда идёт второй getLog).
5. Незаполненная конфигурация больше не приводит к падению с "Unhandled exception":
   Program.cs не бросает исключение из ConfigureServices, а запускает StartupFailureService,
   который пишет понятные записи уровня Critical (консоль, файловый журнал, а при работе
   службой — журнал событий Windows) и штатно завершает приложение с кодом возврата 1.
6. Добавлен StartupConfiguration.cs: проверка конфигурации собирает все замечания сразу
   (Service:db_config, Log:LogFolerPath) с указанием полного пути к appsettings.json
   и примера строки подключения к Firebird.
7. Каталог файлового журнала проверяется пробной записью: если Log:LogFolerPath недоступен
   на запись (нет прав, каталог не создаётся), файловый провайдер молча ничего не писал и
   запись об ошибке запуска оставалась только в консоли. Теперь журнал ведётся в первом
   доступном каталоге (C:\ProgramData\Basip\, каталог приложения, %LOCALAPPDATA%\Basip),
   а причина подмены каталога пишется в сам журнал.
8. Пустой Log:LogFolerPath больше не приводит к необработанному исключению: он попадает
   в общий список замечаний конфигурации (служба не запускается, код возврата 1).
9. Прочие ошибки запуска (например, повреждённый appsettings.json) записываются
   в тот же файл журнала и в консоль через StartupConfiguration.Write, код возврата 1.
10. При каждом запуске в журнал (консоль и файл) пишется версия программы и путь
    к исполняемому файлу: запись делается до старта Worker, поэтому она есть и тогда,
    когда служба не запускается из-за настроек. Определение версии вынесено
    в ApplicationInfo.cs (используется и в Worker, и при старте).
11. Версии приведены к единому значению 2.0.3.7: приложение (Basip.csproj),
    установщик (BasipSetup.iss), build.bat, README.
12. Отладочный вывод, который печатался только в консоль (дамп HTTP-запроса в Device.GetLog,
    диагностика Device.GetEvents, ошибка создания объекта Device), теперь пишется и в файл
    журнала с уровнем Trace. Device получает ILogger через конструктор (передаёт Worker,
    категория Basip.DebugLogCategory), вызовы идут напрямую через logger.LogTrace,
    в начале каждого сообщения указан номер строки исходного кода. Если логгер не передан
    (конструктор без параметров), используется NullLogger и вызовы ничего не пишут.
    Видимость отладки в консоли определяется уровнем Logging:LogLevel.
13. В журнал добавлено явное время следующего запуска: строка "126 timeout basip: ..."
    теперь содержит ", следующий запуск: ГГГГ-ММ-ДД ЧЧ:ММ:СС", а строка "32 basip start: ..."
    — ", первый запуск: ГГГГ-ММ-ДД ЧЧ:ММ:СС" (при run_now = false служба ждёт timestart).
14. В обработчике ошибки создания Device обращение к row["id_dev"] при row = null больше
    не выбрасывает второе исключение: в журнал пишется ID unknown.
15. Каждая строка журнала помечается признаком панели сразу после уровня:
    "[DBG][127] текст" — для записей об обработке панели, "[DBG][sys] текст" — для системных
    записей (версия, старт итерации, таймаут, ошибки запуска, служебные записи хоста).
    Добавлены DeviceContext (id_dev в AsyncLocal), DeviceScopedLogger и
    DeviceScopedLoggerProvider: в состояние записи добавляется свойство id_dev, которое
    подставляет шаблон файлового журнала, а в консоль метка попадает в тексте сообщения.
    Провайдеры журнала оборачиваются в Program.cs, поэтому метка есть и у записей, которые
    создаёт не наш код (Hosting, Application lifetime). Worker обрабатывает панель внутри
    DeviceContext.Set(id_dev), поэтому метку получают записи Worker, DB и Device (включая
    дампы HTTP-запросов). Тексты сообщений при этом не изменялись: если в тексте уже указан
    id_dev=..., он остаётся как есть, метка ставится независимо от него.
16. Log:LogLevel теперь задаёт уровень журнала для наших категорий (Basip.*): Worker, DB,
    Device, Basip.DebugOutput, StartupFailureService. В Program.cs добавлено правило
    logging.AddFilter("Basip", Log:LogLevel), по умолчанию Information. Раньше Log:LogLevel
    применялся только к файловому приёмнику, а общий фильтр MEL (минимум по умолчанию —
    Information) отсекал Debug и Trace: при Log:LogLevel = Trace отладочные записи не
    попадали ни в файл, ни в консоль — в частности, не было видно строки "264 Старт сбор
    событий" и дампов HTTP-запросов. Служебные категории Microsoft.* остаются на Information,
    если в appsettings.json не задана секция Logging.
17. Device.GetLog фиксирует в журнале результат запроса перед возвратом: строка
    "455 GetLog result: status=..., body=..." (уровень Trace) — видно, что именно вернула
    панель на запрос журнала событий. Учтите, что GetEvents вызывает GetLog дважды за цикл
    (пробная страница и последняя), поэтому результат пишется дважды на панель.
18. Адрес и параметры запроса журнала зависят от мажорной версии API панели
    (Device.major_api_version, выставляет Worker из api_version): для 1.x — "log/list"
    с фильтром "filter=timestamp+ge+<мс>", для 2.x и выше — "log/items" с параметром from.
    Из запроса убран sort_type. Панели с прошивкой 3.13.x (api 1.3.5) на "log/items"
    возвращали системный журнал (successful_login_api_call) вместо журнала проходов.
19. Версии приведены к 2.0.4.0: приложение (Basip.csproj), установщик (BasipSetup.iss),
    build.bat. README обновлён: формат строки журнала с меткой [id_dev]/[sys], параметр
    Log:LogLevel для категорий Basip.*, адрес журнала по версии API (log/list для 1.x,
    log/items для 2.x), имя файла журнала с датой, поведение при ошибках запуска,
    раздел про отладку на одной панели.
20. Device.GetEvents собирает события со всех страниц журнала, накопившихся с метки LASTEVENT:
    первая страница (пробный запрос) даёт total_items, далее запрашиваются страницы 2..N,
    их list_items объединяются в один ответ для Worker. Раньше возвращалась только последняя
    страница, поэтому за итерацию обрабатывалось не более limit (50) событий, и накопление
    в 1000 событий требовало 20 запусков. Ограничение — MaxEventPagesPerRun = 200 страниц
    за итерацию (остаток забирается следующей, пишется предупреждение). Ход виден по строкам
    334 (всего событий и страниц), 367 (страница получена) и 370 (собрано событий).
